## 1. Missing Evidence (GAPS)

Based on the Ideal Schema and the provided source extraction, the following structural facts are explicitly present in the code or relationships but missing from the extracted entity definitions:

* **Dangling Relationship Targets (Graph Integrity Failure):** A significant number of `RELATIONSHIP` primitives reference `targetId`s that do not exist anywhere in the `boundaries`, `contracts`, or `openConnectors` arrays. For example:
  * `Require: ./lib/express` points to `81ef29222f13` (Missing).
  * `Express Mount: Root -> path` points to `80c992563923` (Missing).
  * `Inherits: parent.request` points to `cc47bb46d43d` (Missing).
  * The graph is structurally broken because relationships are pointing to phantom nodes.
* **Omitted External/Built-in Boundaries:** The code explicitly imports numerous external dependencies (`finalhandler`, `debug`, `body-parser`) and Node.js built-ins (`node:http`, `node:path`). While `REQUIRE` relationships are extracted for these, the actual external `BOUNDARY` primitives representing these packages are missing, leading to the dangling references mentioned above.
* **Missing Interceptor Guard Representation:** The Ideal Schema explicitly requires that `expressAdapter.ts` captures `router.use()` mounts as "Interceptor Guards" to keep vertical pipelines clean. The current extraction merely creates a generic `MOUNTS` relationship (`router.use(path, fn)`) without representing the middleware function (`fn`) as a boundary or flagging it as an interceptor. 
* **Unresolved HTTP Endpoints / Dynamic Methods:** In `lib/application.js`, Express dynamically assigns HTTP routing methods to the `app` object using a loop (`methods.forEach(function (method) { app[method] = ... })`). The extractor captures a single generic `CJS_METHOD` contract (`Dynamic Export: app[method]`), completely missing the actual semantic HTTP methods (GET, POST, PUT, etc.) that represent the core routing contracts of the framework.

## 2. Architectural Evolutions (EVOLUTIONS)

To align the extraction capabilities with the foundational thesis and Ideal Schema, the following data additions and architectural adjustments are required:

* **Dynamic AST Evaluation for Export Loops:**
  * **Addition:** The extractor must implement lightweight static evaluation or unrolling for known iteration patterns (like iterating over an array of HTTP `METHODS`). Without this, the engine cannot discover dynamically generated `HTTP_ENDPOINT` contracts, which are foundational to tracing vertical execution pipelines.
* **External Entity Stubs (`EXTERNAL_PACKAGE` / `BUILT_IN`):**
  * **Addition:** Add a new `scope` or `entityType` (e.g., `EXTERNAL_PACKAGE`, `NODE_BUILTIN`) for `BOUNDARY` primitives. When a `require()` call targets an import outside the user's lexical repository, a stub boundary must be generated to serve as a valid terminal node for the `REQUIRE` relationship, preventing dangling IDs.
* **Interceptor Relationship Types:**
  * **Addition:** Introduce specific relationship types like `INTERCEPTS`, `GUARDS`, or `WRAPS` to distinguish middleware chains from standard `CALL` or `MOUNTS` relationships. This satisfies the "Horizontal Aspects vs Vertical Pipelines" schema rule, allowing the graph projection to render middleware as badges rather than standard downstream nodes.
* **Graph Integrity Validation Pass:**
  * **Addition:** Implement a post-extraction validation step that enforces referential integrity. If a `RELATIONSHIP` primitive refers to a `sourceId` or `targetId` that was not successfully extracted as a boundary, contract, or open connector, the system must either generate a missing stub node explicitly marked as `INFERRED_UNKNOWN` or drop the invalid edge. "Never manufacture certainty, but represent uncertainty."
